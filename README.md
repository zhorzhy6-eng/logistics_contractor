# Умный конструктор договоров перевозки

Настольное приложение (PyQt5) для подготовки договоров-заявок: вставка текста →
распознавание через GigaChat → заполнение вкладок → генерация DOCX по шаблону →
сохранение в локальную базу SQLite.

## Установка

```bat
pip install -r requirements.txt
```

## Первый запуск: ключ GigaChat

Ключ **не хранится в файлах проекта**. Он сохраняется в системном хранилище
учётных данных (Windows Credential Manager) скриптом `set_key.py`:

```bat
python set_key.py
```

Скрипт попросит вставить `Authorization key` из личного кабинета Sber Developer
Studio (строка Base64). Проверить позже:

```bat
python set_key.py --check
python set_key.py --delete
```

Ключ можно в любой момент отозвать в личном кабинете и записать новый тем же
скриптом — код менять не нужно.

## Зависимости

Всё ставится одной командой `pip install -r requirements.txt`. Что нужно и зачем:

| Пакет | Роль |
|---|---|
| `PyQt5` | интерфейс (`ui/`) |
| `requests` | запросы к GigaChat (`infrastructure/api/gigachat.py`) |
| `python-docx` | чтение/запись DOCX (`core/contract_generator.py`) |
| `docxtpl` | основной шаблонизатор договоров |
| `keyring` | ключ GigaChat в Windows Credential Manager (`infrastructure/secrets/store.py`) |
| `openpyxl` | импорт справочника адресов из Excel |
| `pytest` | тесты (`tests/`), нужен только для разработки |
| `pyinstaller` | сборка `.exe` (`build.bat`), нужен только для сборки |

Python 3.9+; интерфейс и хранилище ключа рассчитаны на Windows.

## Настройки

`config/settings.json` содержит только несекретные параметры (модель, scope,
таймаут, проверка TLS). Образец для нового пользователя —
`config/settings.example.json`:

```bat
copy config\settings.example.json config\settings.json
```

Менять настройки можно в приложении: кнопка **«⚙ Настройки»** (изменения
применяются без перезапуска).

## Запуск

```bat
python main.py
python main.py --debug     :: подробный лог для диагностики
```

Готовые договоры сохраняются в `output/`; после генерации доступна кнопка
**«Открыть папку»**.

При запуске приложение спрашивает **тип договора** — выпадающий список
с пятью пунктами. Рабочий тип — **«Экспедиторство»**: открывается основное
окно (договор-заявка на перевозку). Остальные типы открывают свои рабочие
окна (клиентский тип A, клиентский тип B, клиентский тип D, **клиентский тип C**): у клиентского типа C работают
бэкенд .xlsx (этапы A.1–A.5), шесть вкладок (B.2), окно с генерацией и
распознаванием (B.3) и справка [`docs/README клиентского типа C (приватная часть)`](docs/README клиентского типа C (приватная часть))
(B.4). Отмена выбора закрывает программу.

Тип можно сменить, не перезапуская приложение: селектор **«Тип договора»**
в шапке любого окна переключает окна. Заполненные данные при этом не теряются —
окна не уничтожаются, а прячутся. Штатный выход — кнопка **«Выход»** в шапке:
крестик окна только скрывает его.

## Типы договоров

Тип выбирается при запуске (`ui/contract_picker.py`). Ключи типов — значения
`ContractType` (`core/contracts/contract_types.py`), регистрация — в реестре
(`core/contracts/registry.py`, `BUILTIN_TYPE_MODULES`):

| Пункт списка | Ключ | Окно | Что это |
|---|---|---|---|
| Экспедиторство | `perevozka` | `ui/main_window/` | договор-заявка на перевозку |

Служебный тип `expediciya` («Экспедиторская заявка») остаётся в реестре,
но в списке не показывается.

**Клиентские типы живут в приватной части проекта.** Их окна, генераторы,
валидаторы, промпты распознавания, бланки и инструкции лежат отдельной
папкой (`logistics_contractor_private`), которая не входит в этот
репозиторий. Публичное ядро находит их по обычным именам модулей
(`core.contracts.<ключ>`, `ui.windows.<ключ>`): корень приватной папки
добавляется в `sys.path` вызовом `core.private_path.attach_private_root()`
(см. `main.py`, `tests/conftest.py` и [`docs/PRIVATE_MIGRATION.md`](docs/PRIVATE_MIGRATION.md)).

Приватной папки нет — программа работает в режиме ядра: в списке остаётся
только «Экспедиторство». Это штатный режим, а не ошибка: реестр типов
изолирует сбой импорта каждого типа (`ContractTypeRegistry.failures()`),
промпты отдают `None` (используется дефолтный промпт GigaChat), а список
выбора строится только по зарегистрированным типам.

Порядок пунктов списка живёт в `core/contracts/picker_order.py`, а не в реестре:
там ключи сортируются по алфавиту, а пользователю нужен свой порядок.
Названия пунктов для клиентских типов лежат в приватном
`core/contracts/picker_labels.py`. Оттуда порядок берут и диалог запуска
(`ui/contract_picker.py` реэкспортирует прежние имена `PICKER_ORDER`,
`picker_title`, `picker_items`), и селектор в шапке окна.

Окна типов строятся на общем каркасе `ui/windows/base_window.py`
(`BaseContractWindow`): шапка с названием, селектором типа и кнопкой «Выход»,
сайдбар слева, вкладки из `TAB_CONFIGS` с панелью действий внизу
(«Создать договор», «Очистить клиентского типа A», «Распознать данные»). Панель — общая:
кнопки создаёт каркас, а окно типа решает, что они делают. В публичной части
на каркасе стоит окно «Экспедиторства» (`ui/main_window/` — пакет из 11
модулей, собранный в Этапе 6); окна клиентских
типов приходят из приватной папки и добавляются в фабрики окон
(`main.py::_TYPE_WINDOW_MODULES`) только при её наличии.

Переключение окон — `ui/windows/manager.py` (`WindowManager`): окна создаются
лениво и живут до выхода из приложения. Сигналы окон
(`switch_to_type_requested`, `exit_requested`) ловит `main.py`: селектор просит
переключить тип, кнопка «Выход» закрывает окна (`close_all()`) и завершает цикл
событий. Замыканий в `connect` нет — слоты-методы приёмника держат менеджер
и приложение слабыми ссылками, иначе получается цикл ссылок Python ↔ Qt
и процесс падает при выходе.

Инфраструктура типов:

* `core/contracts/<тип>/` — генератор и валидатор типа; у типов без реализации
  заглушки поднимают `NotImplementedError`, а изолированная загрузка реестра
  не даёт сбою одного типа помешать остальным
  (`ContractTypeRegistry.failures()`);
* `core/prompts/` — `get_prompt(contract_type)`; `None` означает «взять
  дефолтный промпт GigaChat». Модуль промпта ищется по ключу типа, поэтому
  промпты клиентских типов находятся сами, когда подключена приватная папка;
* `core/mirror.py` — зеркало данных «Экспедиторство → клиентский тип»
  (карты переноса — в приватном `core/mirror_targets.py`);
* таблица `counterparties` в `contracts.db` — справочник контрагентов,
  привязанный к типу договора и роли стороны (`db/database.py`: сохранение,
  обновление, поиск, мягкое удаление и восстановление).

Обратная совместимость: `from core.contract_generator import ContractGenerator`
и `GeneratorFactory.get_generator()` без типа по-прежнему дают генератор
договора-заявки на перевозку.

## Интерфейс

Всё оформление собрано в `ui/theme.py` и `ui/theme_palettes.py` (`Fusion`).
Доступны две темы — **«Светлая тема»** и **«Тёмная тема»**; обе используют
общий QSS, различаются палитрой, типографикой и клиентского типа A элементов:

* **навигация — сайдбар слева** (разделы: перевозчик, водитель, тягач
  и полуприцеп, перевозимые авто, договор, заказчик); активный раздел
  выделен полосой и цветом;
* **шапка окна**: селектор **«Тип договора»** переключает окна типов без
  перезапуска приложения, кнопка **«Выход»** завершает работу программы
  (крестик окна только скрывает его — заполненные формы не теряются);
* **тема выбирается в «Настройках»** (блок «Оформление») и сохраняется в
  `config/settings.json`; переключение применяется сразу, без перезапуска;
* **следование за темой Windows** включено по умолчанию: приложение
  повторяет светлый или тёмный режим Windows и переключается, когда режим
  меняется в системе (`ui/system_theme.py`). Выбор темы в списке отключает
  следование — ручной выбор приоритетнее системного;
* **поля сгруппированы в блоки-карточки** с жирным заголовком
  (на вкладке «Перевозчик»: тип, общие сведения, адреса, банковские реквизиты,
  руководитель и контакты, лицензия);
* **главное действие вкладки** — крупная кнопка «🧠 Распознать вкладку»;
  финальное действие «📄 Создать договор» — спокойнее главного;
  вспомогательные («💾 Сохранить в базу», «🧹 Очистить клиентского типа A», «📂 База данных»,
  «⚙ Настройки») — с тонкой рамкой;
* **обязательные поля** помечены звёздочкой цвета акцента (не красной) и подсвечиваются
  фоном предупреждения, пока пусты. Звёздочки соответствуют проверке данных:
  например, КПП обязателен только для ООО — при выборе ИП пометка снимается;
* **статус-бар** показывает, где вы находитесь, сколько полей заполнено на текущей
  вкладке и время последнего сохранения в базу.

Функциональность от оформления не зависит: тема не меняет ни состав полей,
ни их имена, ни порядок работы.

### Ручной ввод и распознавание

Данные можно вводить руками на любой вкладке — распознавание их **не стирает**.
Если в ответе модели блока нет или он пустой (по промпту GigaChat отдаёт
«customer» пустым, а все реквизиты из текста относит к перевозчику), вкладка
остаётся такой, как была. Заполняются только те поля, для которых в ответе
есть непустое значение.

Загрузка записи из справочника («📂 База данных» → «Загрузить в клиентского типа A») —
наоборот, полностью заменяет клиентского типа A данными записи.

### Максимилиан — ИИ-ассистент внутри программы

В шапке окна (правее селектора типа договора) есть **иконка кота** — это
Максимилиан, ассистент-помощник. Иконка открывает **панель диалога** справа:
аватар, история переписки, поле ввода и кнопка «Отправить». Горячая клавиша
по умолчанию — **Ctrl+M**.

Что он умеет (версия 1):

* **объяснять поля**: «что такое ИНН?», «как заполнять код подразделения»;
* **искать в справочниках**: «найди Иванова», «покажи перевозчиков с
  истекающим договором», «какой ВИН у машины А123ВС77»;
* **подтягивать записи в клиентского типа A**: находит водителя или перевозчика и
  переносит его данные на вкладки;
* **распознавать документы**: «что в этом PDF» — через тот же импорт
  документов, что и кнопка «Загрузить документы».

Чего он **не делает**: не создаёт договоры, не удаляет данные, не считает
деньги, не меняет настройки программы, не ходит в интернет никуда, кроме
GigaChat. Заполнение формы он всегда показывает перед записью и спрашивает
подтверждение («Максимилиан хочет заполнить поле… Подтвердить?»).

Как это устроено:

* `core/agent/` — ядро без Qt: `agent.py` (цикл «сообщение → инструменты →
  ответ», не больше 5 шагов на вопрос), `tools.py` (35 инструментов над
  `db/crud/*`), `analytics_tools.py` (сводки, сравнение периодов, топы,
  качество данных), `proactivity_tools.py` (что заполнить дальше, что
  истекает), `proactivity.py` (обязательные поля и порядок заполнения),
  `long_memory.py` (алиасы, привычки, исправления), `prompt.py` +
  `prompts/maximilian.txt` (системный промпт отдельным файлом),
  `personas.py` (образы), `memory.py` (история диалога), `llm.py` (запрос
  к GigaChat с маскированием ПДн);
* `ui/agent_widget.py`, `ui/agent_avatar.py`, `ui/agent_settings_dialog.py` —
  интерфейс: иконка, панель, плавающий кот, настройки;
* история диалога хранится в таблице `agent_history` (сессия = один запуск
  программы), память помощника — в `agent_memory` и `agent_feedback`;
  очищаются кнопками в настройках агента («Забыть всё» чистит только память
  помощника, справочники не трогает);
* **персональные данные перед отправкой в GigaChat маскируются**
  (`core/pseudonymizer.py`), а оригиналы восстанавливаются в ответе.

Отключить помощника можно в «Настройках» → блок «Максимилиан» (или в
`config/settings.json`, раздел `agent`, ключ `enabled: false`): иконка,
панель, кот и горячая клавиша исчезают, запросы к GigaChat не уходят.

Настройки агента (`config/settings.json`, раздел `agent`):

| Ключ | Значение по умолчанию | Что делает |
|---|---|---|
| `enabled` | `true` | включён ли помощник целиком |
| `name` | `"Максимилиан"` | не настраивается: имя зафиксировано |
| `avatar` | `"cat_scientist"` | образ: `cat_scientist`, `cat_logist`, `cat_keeper`, `neutral` |
| `mode` | `"hybrid"` | `icon` (только иконка), `panel` (только панель), `hybrid` |
| `show_floating` | `false` | плавающий кот в правом нижнем углу |
| `show_panel_on_start` | `false` | открывать панель при запуске |
| `hotkey` | `"Ctrl+M"` | горячая клавиша панели |
| `max_history` | `20` | сколько последних сообщений помнит агент |
| `max_tool_steps` | `20` | сколько вызовов инструментов разрешено на вопрос (верхняя граница настройки — 20) |
| `proactive` | `false` | подсказывать без вопроса, чего не хватает в клиентского типа A |
| `proactive_interval` | `300` | пауза между подсказками, секунды |

Кроме лимита шагов запрос ограничен **общим таймаутом 120 секунд** и
**защитой от зацикливания** (три одинаковых вызова подряд без новых данных —
и помощник останавливается). Если сработал любой из трёх предохранителей,
оператор получает человеческий ответ: «Задача большая — не успел за один
запрос. Давай по частям.» и выбор, с чего начать.

## Проверка TLS

Проверка сертификата сервера включена (`gigachat_verify_ssl: true`). Если
GigaChat использует сертификат, которого нет в системном наборе (НУЦ Минцифры),
положите его в `resources/certs/russian_trusted_root_ca.cer` — приложение
подхватит файл автоматически. Подробности: `resources/certs/README.txt`.

## Логи

Папка `logs/` (ротация: 5 МБ × 5 для `app`/`debug`, 2 МБ × 3 для `errors`/`audit`):

| Файл | Уровень | Когда пишется | Что внутри |
|---|---|---|---|
| `logs/app.log` | INFO | всегда | запуск, нажатия кнопок, шаги операций, результаты, предупреждения и ошибки |
| `logs/debug.log` | DEBUG | только с `--debug` | дополнительные технические сведения: запросы GigaChat, SQL, заполненность полей |
| `logs/errors.log` | ERROR | всегда | ошибки с полным traceback |
| `logs/audit.log` | — | всегда | действия пользователя для аудита, без персональных данных |

клиентского типа A строки:

```
2026-09-24 22:15:33 | DEBUG | core.gigachat_client | recognize_text | Отправка запроса, длина промпта: 1523 символов
```

Что видно в `debug.log`: длины промпта и ответа, статус и время каждого запроса,
какие разделы распознали, а какие нет, какие поля заполнены и какие остались
пустыми (только имена полей), текст и время каждого SQL-запроса, каждое нажатие
кнопки и переключение вкладки. Медленные операции помечаются: `SLOW GigaChat`
(дольше 5 с) и `SLOW SQL` (дольше 1 с).

В логи **не попадают**: ключ и токен GigaChat, персональные данные (ФИО, паспорт,
адреса, телефоны), содержимое договора. `@trace` фиксирует только размеры, ключи
и идентификаторы, а сводки заполненности — только имена полей.

Вывод в консоль не ломается на русской кодировке Windows (cp1251): символы,
которых в ней нет, заменяются на `?`, запись в файлы идёт в UTF-8.

## Данные

* `contracts.db` — локальная база (водители, перевозчики, заказчики, ТС, договоры, справочник адресов);
* перед миграциями схемы автоматически создаётся копия в `backup/` (`VACUUM INTO`);
* доступ к базе и папке `logs/` ограничен текущим пользователем Windows.

### Справочник: создание записей вручную

Записи можно заводить прямо в окне «🗄 Управление базой» — кнопкой
**«➕ Добавить»** на вкладках «🚛 Перевозчики», «👤 Водители» и «🏢 Заказчики».
Открывается та же клиентского типа A, что и при редактировании, но пустая и с заголовком
«➕ Новый перевозчик / заказчик / водитель»; у водителя там же заполняются
тягач и полуприцеп — при сохранении они попадут в отдельную таблицу. После
«💾 Сохранить» запись сразу появляется в списке и в базе.

### Справочник: мягкое удаление и связи договоров

Удаление водителя, перевозчика или заказчика в окне «🗄 Управление базой»
**не стирает запись**: она помечается как удалённая (`is_deleted`) и исчезает
из списков и поиска, но остаётся в базе.

* договор сохраняет ссылку на того, кто его исполнял: при сохранении договора
  в `contracts.driver_id` / `customer_id` / `carrier_id` пишутся ID записей
  справочника, поэтому история перевозок не обезличивается;
* данные тягача/прицепа водителя и ТС перевозчика тоже сохраняются;
* вернуть запись можно кнопкой **«♻ Восстановить»**, включив галочку
  **«Показывать удалённые»** (у удалённых строк в колонке «Статус» стоит
  пометка «удалён»);
* полностью стереть запись из базы интерфейс не умеет — это осознанно,
  история перевозок важнее чистоты справочника.

### Поиск в справочниках

Поиск по адресам, водителям и организациям **не зависит от регистра**, включая
кириллицу: запрос «мурманск» находит «Мурманск», «складская» — «Складская»,
«иванов» — «Иванов Иван Иванович».

Как это сделано: в базе есть поисковые индексы FTS5 (`fts_addresses`,
`fts_drivers`, `fts_customers`, `fts_carriers`) с токенизатором `unicode61`.
Индексы не хранят копию данных (external content) и обновляются без триггеров:
при одиночных записях — точечно и сразу, после массового импорта из Excel —
при первом поиске (доливаются только новые строки), поэтому сам импорт
работает с прежней скоростью. Полная пересборка — `db.database.rebuild_fts_index()`.

Что важно знать:

* поиск идёт по словам и их началу («склад» найдёт «Складская») и по городу
  адреса; «ё» и «е» взаимозаменяемы («королев» найдёт «Королёв»);
* середина слова по-прежнему ищется старым способом (LIKE) — как и раньше;
* если FTS5 в вашей сборке Python недоступен, поиск автоматически работает
  по-старому (LIKE) — приложение не ломается;
* запросы с цифрами (паспорт, телефон, ИНН, номер дома) идут старым путём и
  ищутся по подстроке.

Если база копируется вручную, копируйте и файлы `contracts.db-wal`,
`contracts.db-shm` либо делайте копию через `VACUUM INTO`.

# Импорт документов: распознал → проверил → перенёс

Кнопка **«Загрузить документы»** открывает окно «Проверка документов». Пока файлов
нет, в окне — подписанная зона перетаскивания (PDF, DOCX, JPG, PNG); добавьте файлы
кнопкой **«+ Добавить файлы»** или перетащите их в окно и нажмите **«Распознать»**.
Ход работы виден в таблице файлов: «ожидает», «распознаётся…», «готово», «ошибка»
(зелёная, жёлтая, красная и серая строки), а в колонке «Найдено» — сколько полей
прочитано или чем файл не прочитан.

Распознанные поля показаны деревом: сущность (водитель, организация, машина) →
файл-источник → поле, значение и **куда оно попадёт в клиентского типа A** (там же — что в клиентского типа A
сейчас). Галочек подтверждения в окне нет: **переносится всё, что распознано**.
Кнопка **«Перенести в клиентского типа A»** активна, как только есть хотя бы одно распознанное
поле. Чего в документах нет — показано серым «— не найдено —»; такие поля
заполняются в клиентского типа A вручную и перенос не блокируют. Поля с неверным клиентского типа A и
поля, где источники дают разные значения, в клиентского типа A не уходят: окно называет их и
предлагает исправить значение. Если поле формы правили уже после открытия окна,
импорт его не затирает.

Поле правится двойным кликом по строке, правый клик по строке открывает меню:
**«Открыть оригинал»**, **«Показать распознанный текст»**, **«Скопировать значение»**,
**«Удалить строку»** (строка не пойдёт в клиентского типа A) и «Добавить пустые поля вручную».
Кнопка **«Показать распознанный текст»** показывает варианты OCR для файла
или локально извлечённый текст PDF/DOCX. Этот текст доступен только до закрытия окна
и не записывается в журналы. Когда текст есть, но поля не выделены, он помогает
проверить чтение и вручную исправить нужные строки.

Дата принимается также с обычным суффиксом «г.» и переносится в стандартном клиентского типа A.
Импорт не сохраняет договор и справочники в SQLite: сохранение остаётся отдельным
действием пользователя. Полный текст объяснений — в кнопке «?» в правом верхнем углу.

Поддержка клиентского типа A:

| клиентского типа A | Обработка | Требования |
| --- | --- | --- |
| PNG, JPG, JPEG | EXIF-поворот и отправка изображения в GigaChat Vision | Pillow, ключ GigaChat, модель с поддержкой изображений |
| PDF с текстом | Локальное извлечение текста постранично; при непонятном тексте — GigaChat (текст), затем рендер и Vision | pypdfium2 с PDFium, ключ GigaChat |
| PDF с битым текстовым слоем | Страница распознаётся заново: рендер и GigaChat Vision | pypdfium2, ключ GigaChat |
| Сканированный PDF | Локальный рендер страниц, затем GigaChat Vision | pypdfium2, ключ GigaChat |
| DOCX | Абзацы, таблицы, текст колонтитулов локально | python-docx |
| DOC | Локальное преобразование в DOCX во временной папке | LibreOffice (путь к soffice) или установленный Microsoft Word |
| RTF | Локальное извлечение текста без макросов | — |
| ZIP | Распаковка во временной папке, затем обработка вложенных файлов | — |
| RAR | Распаковка UnRAR во временной папке, затем обработка вложенных файлов | WinRAR/UnRAR |

Установите Python-зависимости командой `python -m pip install -r requirements.txt`.

### Распознавание изображений через GigaChat Vision

Изображения документов (PNG, JPG, JPEG) и растрированные страницы сканированных
PDF отправляются в **GigaChat Vision** — облачный режим GigaChat, который умеет
«видеть» картинки и извлекать из них структурированные данные.

**Что нужно:**
- ключ GigaChat в Windows Credential Manager (тот же, что для текстового
  распознавания; сохраняется через `python set_key.py`);
- модель с поддержкой изображений: **GigaChat-3-Pro** или **GigaChat-3-Ultra**
  (GigaChat-3-Lightning картинки не обрабатывает — API отвечает
  «422 Model does not support image»);
- активная настройка **«Разрешить отправку изображений в GigaChat»** в окне
  настроек (`document_cloud_enabled: true`).

**Как это работает:**
1. Приложение загружает изображение в хранилище GigaChat через `/files`.
2. Отправляет его в `/chat/completions` в массиве `attachments` вместе с
   промптом, который требует строгий JSON по заданной схеме.
3. Если JSON пришёл валидным, но без данных, приложение сначала просит
   транскрипцию изображения и извлекает поля из текста, а для нечитаемых
   снимков повторяет запрос с усиленным контрастом и резкостью.
4. Получает структурированный ответ и раскладывает поля по вкладкам.
5. После обработки (успех, ошибка, отмена) вызывает `/files/{id}/delete`,
   чтобы удалить изображение из хранилища API.

Изображения и распознанный текст **не записываются в логи приложения**.

**Роли и точность:**
По умолчанию все реквизиты организации из документа относятся к **перевозчику**
(блок `carrier`), а `customer` остаётся пустым — если только в документе явно
не написано «Заказчик». ИП и ООО определяются автоматически, НДС по умолчанию
считается 22%. Тягач и полуприцеп выделяются в отдельные блоки, а не в общий
список `vehicles`. Нечёткие цифры (VIN, ИНН, счета, паспорт) не восстанавливаются —
такие поля остаются пустыми до ручной проверки.

**Ограничения:**
- Модель может ошибаться на бликах, мелком тексте и сильной перспективе.
  Распознанные поля видно в окне импорта до переноса в клиентского типа A — проверяйте их
  по оригиналу (правый клик по строке → «Открыть оригинал»).
- Если GigaChat Vision недоступен (нет ключа, выключен облачный режим или модель
  не поддерживает изображения), изображение не обрабатывается и файл получает
  понятную ошибку. При выключенном облаке используется локальный OCR.
- Локальный OCR (Tesseract) остаётся как fallback для офлайн-режима: нужен
  пакет `pytesseract` (ставится с зависимостями) и сам движок Tesseract OCR
  в `PATH`.

Для PDF отдельные Poppler и Ghostscript не нужны: PDFium поставляется с pypdfium2.

Для старого DOC установите LibreOffice и укажите путь к `program/soffice.exe`
в настройках (либо добавьте его в PATH) — либо используйте установленный
Microsoft Word: приложение умеет конвертировать DOC через Word автоматически.
Без любого из них DOC принимается в очередь, но получает понятную ошибку;
остальные файлы продолжают обрабатываться. DOCX со встроенными фотографиями,
текст в фигурах Word, рукописные записи и PDF под паролем не гарантируются.
Ограничения импорта: 50 МБ на файл, 100 страниц PDF, 40 мегапикселей на исходное
изображение, 100 МБ и 50 файлов на распакованный архив.

## Облачный режим и отмена

Настройка `document_cloud_enabled` включает отправку изображений и растрированных
страниц в GigaChat Vision (в примере `config/settings.example.json` этот режим уже
включён; снять галочку **«Разрешить отправку изображений в GigaChat»** можно в окне
настроек). Нужны ключ GigaChat и модель с поддержкой изображений
(GigaChat-3-Pro или GigaChat-3-Ultra).

Текстовая страница обрабатывается локально. Если локальные правила не нашли
полей и включён облачный режим, её текст отправляется в GigaChat текстовой
модель, а для PDF дополнительно допускается рендер страницы и Vision. При
выключенном облаке текстовые документы в сеть не уходят.

Отмена кооперативная: уже начатая операция завершается или достигает таймаута.
После этого выполняется удаление файла из хранилища GigaChat через
`/files/{id}/delete`. Окно не закрывается до завершения очистки. Ошибка одного
файла не отменяет обработку остальных.

Протокол работы с файлами: [документация GigaChat](https://developers.sber.ru/docs/ru/gigachat/guides/working-with-files).

## Точность и ограничения сопоставления

Локальный разбор поддерживает подписанные реквизиты, карточки контрагентов,
свидетельства ИНН/ОГРН, листы записи ЕГРЮЛ, многострочные поля паспорта РФ,
водительские карточки, регистрационные документы ТС и банковские реквизиты.
Битый текстовый слой (латиница вместо кириллицы, мусорные глифы) распознаётся
как непригодный: такая страница рендерится и уходит в Vision. GigaChat Vision
возвращает структурированный JSON, локальный OCR (Tesseract) — текст; оба варианта
сопоставляются с полями формы без восстановления нечитаемых символов. Это не
универсальное понимание иностранных документов. Нечитаемые номера не
восстанавливаются; некорректные даты и идентификаторы не допускаются
к переносу. Проверка клиентского типа A не доказывает, что номер прочитан правильно.
Варианты разных источников сохраняются в таблице, конфликтное значение остаётся
пустым до ручной правки. Совпадение текста и распознанного изображения также
остаётся на проверку оператора — но перенос это не блокирует: подтверждающих
галочек в окне нет.
Собственник ТС не назначается водителем; ИНН банка не используется как ИНН перевозчика.
Для личных банковских реквизитов показана подсказка проверить получателя и назначение
счёта. Диагностика содержит число символов, вариантов и полей, без распознанного текста.

Сначала группируются записи по совпадающим признакам (ФИО с проверкой даты рождения,
ИНН/наименование, VIN/госномер, номер договора). При конфликтующих идентификаторах
или отсутствии признаков записи остаются раздельными. VIN разных машин не сравниваются
по позиции в массиве. Одинаковые имена/названия всё ещё требуют проверки человеком.
Для перевозчика/заказчика и существующего автомобиля можно изменить цель всей группы.
Группы с противоречащими идентификаторами нельзя перенести в одну целевую запись.
Если связь не установлена из-за отсутствующих идентификаторов (например, паспорт,
ВУ и отдельная страница регистрации), перенос требует отдельного подтверждения,
что выбранные группы относятся к одной записи. Новые автомобили
добавляются без очистки существующих строк, неизвестные год и тип остаются пустыми.
Многострочные маршруты погрузки/выгрузки в этом импорте не реконструируются; доступны
скалярные поля договора, включая плановые даты. Если поля не выделены вообще,
показывается «— не найдено —»; пустые поля нужной вкладки добавляются правым кликом
(«Добавить пустые поля вручную») и заполняются вручную, сверяясь с оригиналом.

Блики, мелкий текст, перспектива и несколько языков ограничивают качество даже
облачного OCR. Проверка клиентского типа A номера не подтверждает правильность каждой цифры.
Личные фотографии не входят в репозиторий и автоматические тесты; платные запросы
с ними запускаются только пользователем в приложении.

Тесты импорта: `python -m pytest tests/test_document_import.py tests/test_document_layouts.py -ra`.
Они используют синтетические документы и подменённые сетевые ответы, проверяют
извлечение, группировку, конфликты, защиту формы, отмену и очистку вложений.
