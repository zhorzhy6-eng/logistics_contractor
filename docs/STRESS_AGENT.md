## Почему в отчёте 80 запросов из 200, а критичных находок «0»

Главная находка стресс-теста — **падение программы**, а падение в записи
попасть не может: процесс умирает, и записывать в JSON уже некому. Поэтому
она описана здесь руками, с доказательствами.

### 🔴 №1. Программа падает во время ответа: панель обновляется из чужого потока

`AgentWidget._panel_call` вызывался из РАБОЧЕГО потока (там работает агент)
и «передавал» вызов в интерфейс через
``QTimer.singleShot(0, lambda: func(*args))``. Но таймер, созданный в
рабочем потоке, срабатывает В НЁМ ЖЕ — то есть панель (виджет!) менялась из
чужого потока. В консоли оставалось ровно это:

```
QObject::setParent: Cannot set parent, new parent is in a different thread
QObject::killTimer: Timers cannot be stopped from another thread
```

и процесс завершался с кодом `0xC0000005` (access violation) — без traceback.
За прогон так умерли три запуска: на запросах №34, №58 и №81.

Доказательство (A/B, `tests/_tmp/_stress_agent/_probe_activity_ab.py`):
один и тот же сценарий «шаг агента из рабочего потока» на старом коде даёт
`0xC0000005`, на новом — вызов приходит ровно один и ровно из главного
потока.

### 🔴 №2. Диалог подтверждения создавался в рабочем потоке (и ронял процесс)

Инструмент `parse_and_fill` (автозаполнение формы из текста — главная
возможность Максимилиана) спрашивает подтверждение диалогом превью. Диалог
создавался прямо в `_confirm`, то есть в РАБОЧЕМ потоке, да ещё и с
родителем из главного (`self.panel`). Qt отказывался усыновлять виджет
(«Cannot set parent, new parent is in a different thread»), диалог оставался
«ничейным» — и программа падала.

Падало **устойчиво**: три попытки прогона подряд умерли на №81 (первый
запрос автозаполнения), прогресс не сдвинулся ни на запись:

```
попытка 1 завершилась: код -1073741819, записей 80
попытка 2 завершилась: код -1073741819, записей 80
попытка 3 завершилась: код -1073741819, записей 80
попытка 4 завершилась: код -1073740940, записей 80
ПРОГРЕСС ВСТАЛ — останавливаюсь
```

То есть у оператора это выглядело бы так: он вставляет текст с данными,
просит «заполни» — и программа исчезает вместе с несохранённой формой.

История диалога в рабочей копии базы подтверждает, на чём именно умерло
(последняя запись перед падением):

```
[745] user      Перевозчик: ООО «Ромашка» … Вины: XTA21093053810234 …
[746] assistant → parse_and_fill {"text": "Перевозчик: ООО «Ромашка» …"}
```

### 🟡 №3. Один плейсхолдер маски — два разных значения

Запрос №7: оператор сказал «Найди», а Максимилиан ответил разбором слова
«Заполни» — то есть ответом на предыдущий вопрос. Причина видна в истории
диалога: маска ПДн закрывает короткие сообщения целиком
(«Заполни» → `<<PERSON_1>>`, «Отмени» → тоже `<<PERSON_1>>`), потому что
каждое сообщение маскировалось своим маппингом, а маппинги сливались через
`dict.update`. В модель уходили два РАЗНЫХ сообщения одним и тем же текстом
`<<PERSON_1>>`, а `restore` возвращал то значение, которое попало в маппинг
последним: инструмент получал слово из ЧУЖОГО сообщения.

Механизм доказан минимально:

```
user -> '<<PERSON_1>>'      (было «Заполни»)
user -> '<<PERSON_1>>'      (было «Отмени»)
маппинг: {'<<PERSON_1>>': 'Отмени'}
restore('<<PERSON_1>>') -> 'Отмени'   # для первого сообщения — неверно
```

### 🟡 №4. Незакрытый блок инструментов ломал следующий запрос

`AgentMemory.wire_messages` хранил начало блока инструментов как индекс в
СПИСКЕ ЗАПРОСА, а проверял «все ли вызовы получили ответ» по СПИСКУ ИСТОРИИ
(`self._messages[block_start]`). Списки не совпадают (системный промпт
добавляет элемент, «висячие» результаты инструментов пропускаются), поэтому
проверялось ЧУЖОЕ сообщение, и недопустимая история уходила в GigaChat.
Найдено перебором историй: 7431 история, 5 расхождений с эталоном.

### 🟡 №5. Служебный ответ по лимиту шагов — отладочный дамп

Запросы №22, №23, №31: когда модель зовёт инструменты больше лимита (3
шага), ответ оператору формируется без модели — и в него попадали машинные
имена инструментов и `repr` их данных:

```
Дошёл до лимита в 3 шагов — дальше звать инструменты не буду.
Успешно выполнено: 3. Что нашёл:
• get_form_state: carrier_tab={'filled': {'license_date': '2026-10-15', …
```

2121 символ внутренней кухни вместо ответа.

### 🟢 №6. Ложные срабатывания маски на словах-командах

«Заполни», «Отмени», «Удали» — обычные слова-команды, но NER-модель считает
их именами, и сообщение целиком уходит под маску: модель не видит просьбу
оператора (№26 «Удали» → ответ «Отменить что именно?»). Это точность
детектора в `core/pseudonymizer.py` — файл AGENTS.md § 4 относит к «спроси
перед изменением», поэтому правка не делалась; предложение записано в
`docs/STATE.md`.

## Что дал прогон по существу

На 80 дошедших запросах модель ведёт себя хорошо: 80 из 80 без ошибок, 52 с
вызовом инструментов, поиск (B.3) — 20 из 20 с инструментом, аналитика
(B.4) — 16 из 20. Ни одного выдуманного действия, ни одной выдуманной
цифры, ни одной нормы «по памяти», база оператора не изменилась
(счётчики таблиц и `integrity_check` сверены до и после — вручную, потому
что при падении процесса `db_after` записать некому).

Слабые места — не поиск и не аналитика, а **команды без объекта** (B.2:
6 находок на 20 запросов) и **редкие виды аналитики** (B.4: 4 находки —
«Процент выполненных договоров», «Сколько убыточных договоров»,
«Динамика по месяцам», «Покажи статистику»): там модель вместо вызова
инструмента начинает уточнять вопрос. Это 🟡: ответ неверный, но не
вредный.
