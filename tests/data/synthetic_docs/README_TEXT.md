# Стресс-тест распознавания ТЕКСТА — 1000 сценариев

Артефакты текстового стресс-теста: **зёрна** генератора и **baseline**
метрик GigaChat-3-Pro. Оба файла содержат только числа, имена полей и
раскладку — значений из документов в них нет.

> **Здесь нет персональных данных.** В `text_seeds.json` — 1000 целых чисел
> и раскладка «номер → вид → уровень»; в `baseline_text_gigachat.json` —
> recall / precision / F1 и имена полей вида `driver.full_name`. Сами тексты
> собираются прогоном и на диск не пишутся вовсе. Правило — `AGENTS.md` § 4.

## Чем этот стресс-тест отличается от картиночного

| | `synthetic_docs` (картинки) | `synthetic_docs` (текст) |
|---|---|---|
| Что на входе | PNG-бланк | готовый текст |
| Что проверяется | весь конвейер: чтение → OCR → разбор | только разбор |
| Модель | GigaChat-3-Pro (Vision) | GigaChat-3-Pro (текст) |
| Ошибки OCR | смешаны с ошибками разбора | отсутствуют |

Второй тест нужен, чтобы отделить «модель не разобрала текст» от «OCR не
прочитал буквы»: в картиночном прогоне эти причины неразличимы.

## Состав

| Файл | Что это |
|---|---|
| `text_seeds.json` | 1000 зёрен + раскладка по видам и уровням сложности |
| `baseline_text_gigachat.json` | метрики GigaChat-3-Pro и локального разбора: overall, по видам, по уровням, по полям |
| `baseline_text_gigachat_1000.json` | те же 1000, но с разбором ОШИБОК: топы `missed` / `wrong` / `extra` по полям, партии «до фикса» и «после фикса», замер маски. Собирается командой `--report` |

## Раскладка покрытия

| Вид | Сценариев | simple | medium | hard | extreme |
|---|---:|---:|---:|---:|---:|
| `drivers` — водитель, паспорт, ВУ | 250 | 75 | 90 | 65 | 20 |
| `vehicles` — автомобиль, тягач, полуприцеп | 250 | 75 | 90 | 65 | 20 |
| `organizations` — реквизиты, банк, директор | 250 | 75 | 90 | 65 | 20 |
| `addresses` — адреса точек и регистрации | 100 | 40 | 35 | 20 | 5 |
| `documents` — смешанные документы | 150 | 50 | 50 | 35 | 15 |

Порядок сценариев **перемешан детерминированно**: прогон идёт пять часов и
может оборваться на лимите запросов, поэтому первые N сценариев должны быть
представительными, а не «250 водителей подряд».

## Уровни сложности

| Уровень | Что добавляется |
|---|---|
| `simple` | стандартная запись: «ФИО: Иванов Иван Иванович», паспорт «18 22 926830», VIN из 17 допустимых символов |
| `medium` | лишние пробелы внутри значений, « : » в метках, номера через дефис, реквизиты банка |
| `hard` | дефисные ФИО и двойные имена, слитные номера («Паспорт 4712553107»), реквизиты подряд одной строкой |
| `extreme` | апострофы (О'Брайен), нерусские имена (Ли Пэн), кириллица и буквы I/O/Q в VIN, опечатки в метках («ВИН», «Г/н», «Тел.») |

## Как это работает

1. **Зерно → текст.** `tools/make_text_scenarios.py::build_scenario(rng, kind, level)`
   собирает текст из закрытых словарей модуля. Одно и то же зерно даёт один и
   тот же текст побайтово — на этом держится регрессия.
2. **Текст → поля.** Облако: `GigaChatClient.recognize_text` (с обезличиванием
   внутри). Правила: `core.document_import_service.extract_local_fields`.
3. **Поля → метрика.** `tools/synthetic_stress.py::score` — та же формула, что
   у картиночного стресс-теста: `recall = tp / expected`,
   `precision = tp / found`, `f1`.

## Команды

```bash
# 1. Пересобрать зёрна (нужно только при изменении раскладки)
python tools/make_text_scenarios.py --write-seeds

# 2. Посмотреть сценарии глазами (метки и эталон)
python tools/make_text_scenarios.py --show 5

# 3. Только локальный разбор — бесплатно и мгновенно
python tools/run_text_stress_gigachat.py --local-only

# 4. Проверки безопасности по всей выборке, без запросов
python tools/run_text_stress_gigachat.py --dry-run

# 5. Полный прогон 1000 сценариев и запись baseline (~5,3 часа, один поток)
python tools/run_text_stress_gigachat.py --write-baseline

# 6. Продолжить прерванный прогон (повторных запросов не будет)
python tools/run_text_stress_gigachat.py --resume --write-baseline

# 7. Быстрая проверка на выборке
python tools/run_text_stress_gigachat.py --sample 20

# 8. Метрики по всему прогрессу: топы ошибок по полям, партии «до/после
#    фикса», замер маски — без сети, ключ не нужен
python tools/run_text_stress_gigachat.py --report

# 9. Замер ОДНОГО фикса: переспросить только те сценарии, где есть нужное
#    поле эталона (~2 часа на 400 сценариев), и сравнить с копией прогресса
copy tests\_tmp\_text_stress_progress.json tests\_tmp\_before.json
python tools/run_text_stress_gigachat.py --resume --reask ^
    --with-field driver.passport_series
python tools/run_text_stress_gigachat.py --report ^
    --compare-with tests\_tmp\_before.json ^
    --compare-fields driver.passport_series,driver.passport_number
```

`--with-field` можно повторять (выборка — объединение), `--reask` сбрасывает
сохранённые ответы ТОЛЬКО по выборке, `--compare-with` печатает «было →
стало» по каждому полю и общим метрикам. Ответы модели в прогрессе не
хранятся — только `field_stats` (сколько раз поле было в эталоне, найдено,
совпало, пропущено, испорчено), поэтому переприменить локальный слой к
сохранённым ответам невозможно: замер требует повторного запроса.

Прогонщик возвращает код 1, если recall упал больше допуска (0.02), и код 2,
если остановила проверка безопасности, ключ или лимит запросов.

## Метрики: две precision

Формула `score` считает найденным любое непустое поле ответа. Но системный
промпт **требует** ставить `vat_rate = 22 %`, `payment_days = 10`,
`price_without_vat = 0` и год выпуска `0`, даже когда их в документе нет:
для приложения это настройки, а не данные (см.
`GigaChatClient._has_meaningful_values`). Поэтому в baseline две precision:

* `precision` — по формуле `score` (служебные подстановки считаются лишними);
* `precision_core` — без них: `tp / (found − service_filled)`.

Разница между ними — мера того, сколько «лишних» полей дописывает промпт.
Значения `service_filled` и имена полей лежат в baseline рядом.

> **Поле `requests` в baseline — только последняя сессия прогонщика.**
> `--resume` начинает счётчики с нуля, поэтому в файле может стоять
> `{"requests": 1}`, хотя всего сценариев обработано больше тысячи. Число
> ответов (`answered`) при этом верное: оно считается по прогрессу.

## Безопасность прогона

Перед каждым запросом (код 2 при нарушении):

1. ни одно значимое значение сценария не встречается в рабочей `contracts.db`
   (`LIKE`-подстрока, включая вариант «только цифры»);
2. в тексте нет путей и имён файлов оператора;
3. `Pseudonymizer.anonymize()` вернул непустой маппинг, а персональные
   значения (ФИО водителя и директора, паспорт, ВУ, телефон, адрес
   регистрации, место рождения) закрыты плейсхолдерами.

После ответа: в результате не осталось `<<...>>`.

**Что НЕ закрывается плейсхолдером** (проверено на 1000 сценариев):
название организации, ОГРН, ОГРНИП, расчётный и корреспондентский счёт, БИК,
метка «Заказчик». Это не персональные данные, но и не «ничего»: если политика
изменится, расширять надо `core/pseudonymizer.py` (правка согласуется
отдельно — `AGENTS.md` § 4).

**Баг № 1 — маска заходила на следующую строку — ПОЧИНЕН 12.10.2026**
(коммит `0cbf386`, тесты `tests/test_pseudonymizer.py`).
В шаблонах ФИО и адреса разделитель был записан как `\s`, а в него входит и
перевод строки; у адреса ещё и необязательный «хвост». Маска захватывала
перенос строки и начало СЛЕДУЮЩЕЙ строки:

```
Место рождения:г. Мурманск, ул. Центральная      <<ADDRESS_1>> <- 'г. Мурманск, ул. Центральная\nТелефон:+7'
Телефон:+7 (934) 923-84-26                  ->  Место рождения:<<ADDRESS_1>> <<PHONE_1>>
```

Из-за этого метка «Телефон:» не доходила до модели, и поле
`driver.birth_place` давало 0.00 у облака против 0.74 у правил (это НЕ ошибка
модели). Тем же способом портились «Адрес регистрации» (`<<ADDRESS_2>>` +
`ОДИТЕЛЬСКОЕ УДОСТОВЕРЕНИЕ`), «Кем выдан» и «Код подразделения».

Что сделано:

* `\s` → `[^\S\n\r]` (горизонтальный пробел: табуляция — да, перевод строки —
  нет) в `_PERSON_THREE_RE`, `_PERSON_TWO_RE`, `_PERSON_INITIALS_RE`,
  `_ADDRESS_STREET_RE`, `_ADDRESS_HOUSE_RE`, `_ADDRESS_FLAT_RE`;
* дефис и апостроф стали ЧАСТЬЮ слова ФИО (`_PERSON_WORD`): «О'Брайен» и
  «Иванов-Петров» — одно слово, а не два; иначе маска стартовала с середины
  фамилии, а её начало уходило в облако открытым текстом.

Измерено на тех же 1000 текстах, без модели (проба
`tests/_tmp/_probe_mask_newline.py`, те же числа пересчитывает
`--report`): масок с переносом строки внутри было
**171**, стало **1**; из них с меткой поля внутри маски — **100 → 0**.
Затронуты были ровно те поля, что названы пострадавшими: «Место рождения»,
«Телефон», «Кем выдан», «Код подразделения», «Адрес регистрации».

Что это дало в метриках (recall облака, партия «264» — до фикса, «736» — после;
партии состоят из разных сценариев, поэтому это не «до/после» на одних
текстах, но по названным полям картина однозначная):

| Поле | до фикса | после фикса |
|---|---:|---:|
| `driver.birth_place` | 0.00 (0/40) | **0.97** (92/95) |
| `driver.phone` | 0.64 (55/86) | **1.00** (189/189) |
| `driver.passport_code` | 0.60 (24/40) | **0.98** (93/95) |
| `driver.passport_issuer` | 0.85 (73/86) | **1.00** (189/189) |
| `driver.registration_address` | 0.93 (69/74) | 0.99 (178/180) |
| `driver.full_name` (апостроф) | 0.97 (115/118) | 1.00 (281/282); на `extreme` 21/22 против 13/22 у правил |

Остался один хвост — и это **не регулярки, а слой Natasha**: PER-спан сам
может содержать перенос строки (#697, единственный такой сценарий из 1000),
а NER иногда принимает за фамилию служебное слово (#680: «Паспорт», «Марка»).
Это поведение чужой модели, а не шаблонов; правка — отдельная задача
(`_find_person_natasha`).

**Баг № 3 — серия и номер паспорта — ПОЧИНЕН 13.10.2026** (коммит `addc869`,
тесты `tests/test_pseudonymizer.py` — 33 новых). Серия и номер, РАЗДЕЛЁННЫЕ в
тексте («58 38 312160», «5838 312160», «58 38 №312160», «4712№553107»),
закрываются теперь ДВУМЯ плейсхолдерами — `<<PASSPORT_SERIES_N>>` и
`<<PASSPORT_NUMBER_N>>`; разделитель между ними остаётся в тексте, поэтому
модель видит границу полей. Слитная запись («5838312160») делить нечем —
там остаётся один `<<PASSPORT_N>>`, а пару раскладывает
`core.gigachat_client._normalize_document_ids` после восстановления.

Что важно в разборе этого бага (проверено по данным, не на глаз):

* прежнее объяснение «модель делит восстановленную строку сама» — неточное:
  пару раскладывал `_normalize_document_ids` УЖЕ ПОСЛЕ ответа, поэтому
  `wrong` и был нулём. Настоящая потеря — когда модель не возвращала токен
  вообще (все 132 пропуска имеют `found = 0`);
* по уровням пропуски распределены так: `simple` 77, `medium` 33,
  `extreme` 19, `hard` 3 из 100 — то есть 129 из 132 пропусков приходятся на
  форматы, где серия и номер РАЗДЕЛЕНЫ и где маска теперь даёт два токена;
* локальный замер без модели (`tests/_tmp/_probe_passport_split_measure.py`):
  из 400 сценариев с паспортом **300 получают два токена**, 100 (уровень
  `hard`, слитная запись) — один; открытых цифр серии и номера — **0**;
  контроль фикса `0cbf386` — сценариев с переносом строки внутри маски
  по-прежнему 1;
* дополнительно починен `_BARE_TOKEN_RE`: подчёркивание входит в имя токена,
  иначе `PASSPORT_SERIES_1` без угловых скобок не восстанавливался (нашёл
  собственный новый тест).

**Баг № 5 — `vehicles.vehicle_type` — ПОЧИНЕН 13.10.2026** (коммит
`8983261`). Причина оказалась НЕ в разборе и не в отсутствии метки: метка
(«Тип ТС», «Вид ТС», «Тип транспорта») есть во всех 275 сценариях. Пропуски
распределены по значению поля так:

| Значение `vehicle_type` | Пропущено | Найдено |
|---|---:|---:|
| `Тягач` | **49** | 3 |
| `Прицеп` | 1 | 51 |
| `Легковой автомобиль` | 1 | 50 |
| `Фургон` | 0 | 51 |
| `Автобус` | 0 | 58 |

То есть терялось РОВНО значение «Тягач». Виновато правило системного промпта
«Тягач и полуприцеп НЕ добавляй в массив `vehicles` — они идут в отдельные
блоки `tractor` и `trailer`»: модель понимала его как запрет на значение поля
`vehicle_type`. Правило уточнено — оно про БЛОКИ текста (заголовки «ТЯГАЧ»,
«ПОЛУПРИЦЕП»), а не про значение поля, и приведён пример
«Тип ТС: Тягач» → `vehicle_type = "Тягач"`.

**Баг № 6 — банк и директора — ПОЧИНЕН 13.10.2026** (коммит `248b36b`).
Одна причина на все три поля: в «сложных» текстах метка стоит БЕЗ двоеточия, и
модель кладёт её в значение.

| Поле | Неверных | Где именно |
|---|---:|---|
| `carrier.bank_name` | 8 из 96 | 7 — уровень `hard`, реквизиты одной строкой: «Р/с … БИК … К/с … Банк ПАО «Промсвязьбанк»» |
| `carrier.director_name` | 14 из 96 | 13 — уровень `extreme`, «Руководитель Иванов Иван Иванович», «Директор. Петров Пётр Петрович» |
| `customer.director_name` | 9 из 19 | 9 — уровень `extreme` |

Сделано две половины: постобработка `_normalize_labeled_values`
(`core/gigachat_client.py`) снимает слово-метку у `bank_name` и
`director_name` в разделах `carrier` и `customer` — только метку, только если
после неё осталось значение (у ФИО минимум два слова), входной словарь не
меняется; и в системный промпт добавлены примеры с разбором строки реквизитов
и меток без двоеточия. У `customer.director_name` остаётся вторая причина, не
связанная с меткой: в части сценариев эталона организация — ИП, а рядом стоит
строка «Руководитель <другое ФИО>» с должностью «Генеральный директор»; ИП с
наёмным генеральным директором — артефакт генератора сценариев (см. «Требует
решения»).

**Баг № 7 — `driver.birth_place`: «облако хуже правил» — РАЗОБРАН
13.10.2026** (коммит `ed6fae1`). Это НЕ свойство модели, а артефакт
смешанного baseline. По партиям (1000 сценариев):

| Партия | Движок | было в эталоне | найдено | совпало | пропущено | неверно |
|---|---|---:|---:|---:|---:|---:|
| 264 (до фикса `0cbf386`) | облако | 38 | 28 | 0 | 10 | **28** |
| 736 (после фикса) | облако | 95 | 92 | **92** | 3 | **0** |
| 1000 всего | облако | 135 | 122 | 92 | 13 | 30 |
| 1000 всего | правила | 135 | 135 | 100 | 0 | 35 |

В партии «после фикса» облако даёт **0.97** против **0.77** у правил —
то есть облако УЖЕ лучше, а «0.68 против 0.74» получается только при
складывании партий, где 264 ответа сняты старым (битым) псевдонимизатором.
Проверены и отброшены все три гипотезы задания:

* «модель возвращает с префиксом «г.»» — нормализация метрики снимает «г»,
  «ул», «д», «кв», «обл», «край», «респ», регистр и любые разделители:
  «г. Москва, ул. Тестовая» и «Москва, Тестовая» — одно значение (тест в
  `tests/test_recognition_birth_place.py`);
* «модель путает с `registration_address`» — в 43 проблемных случаях адрес
  регистрации разобран верно;
* «модель обрезает» — проба `tests/_tmp/_probe_birth_place_masks.py`: во всех
  43 случаях подпись «Место рождения» в маске ЖИВА и переносов строки внутри
  маски нет; то есть обрезать значение маска не могла.

Остались 3 пропуска из 95 в партии «после» (`#258`, `#410`, `#943` и `#697`) —
все `extreme`. В этих текстах модель не заполнила не только место рождения, но
и паспортную пару с ВУ: поле потеряно не меткой и не маской, а целиком
«провалившимся» ответом на длинный текст. Для `#697` отдельно остаётся хвост
Natasha (перенос строки внутри PER-спана) — та же отдельная задача, что и
`#680`. Добавлено правило промпта про метку без двоеточия для ВСЕХ полей.

**Баг № 4 — формат паспорта словами (пробел покрытия теста).**
Паспорт, записанный как «серия 47 12 номер 553107», детектор
`_DOC_NUMBER_RE` не ловит: между серией и номером стоит слово. В стресс-тесте
такой формат не используется (иначе номер уходил бы в облако открытым), но в
реальных документах он встречается — это отдельная задача.

* `contract.price_without_vat` (955), `payment_days` (905), `vat_rate` (905),

отдельно. Настоящих лишних полей в топе мало: `carrier.short_name` (61),

разделе), `tractor.brand_model` / `color` / `plate_number` (по 6).

## Что делать, если baseline «поехал»

1. `python tools/run_text_stress_gigachat.py --resume` печатает расхождения
   по видам, уровням и полям.
2. `python tools/run_text_stress_gigachat.py --report` собирает топы ошибок по
   полям и партии «до/после фикса» — сеть и ключ не нужны.
3. Разобрать конкретные сценарии: `tests/_tmp/_text_stress_progress.json`
   хранит по каждому номеру `missed` / `wrong` / `extra` — только ИМЕНА полей.
4. Падение — следствие осознанной правки (промпт, разбор, псевдонимизатор)?
   Обновить baseline (`--write-baseline`) и объяснить причину в `docs/STATE.md`.
5. Падение неожиданное — искать причину, а не обновлять baseline.

## Чего здесь делать НЕЛЬЗЯ

- Класть в эту папку тексты документов: папка идёт в git.
- Класть в `text_seeds.json`, `baseline_text_gigachat.json` и
  `baseline_text_gigachat_1000.json` значения полей — даже синтетические:
  файлы читают как «только числа и имена полей» (проверяется тестами
  `tests/test_make_text_scenarios.py` и `tests/test_run_text_stress_gigachat.py`).
- Отправлять в облако реальные документы: тексты собираются генератором,
  а сверка с рабочей `contracts.db` не даёт отправить чужое.
