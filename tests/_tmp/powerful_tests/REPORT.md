## Критичные проблемы

### 1. ИСПРАВЛЕНО: импорт документа не работал ВООБЩЕ

`services/recognition/import_service.py::DocumentImportService.process()`
падал `NameError: name 'read_document' is not defined` на **любом** файле.
Оператор видел «Не удалось прочитать файл: повреждение, пароль или нет
доступа.» — сообщение, уводящее от настоящей причины.

* **Причина:** при переезде 1.G (`66617df`) `read_document` стал приходить
  лениво через модульный `__getattr__` (PEP 562). А `__getattr__`
  срабатывает ТОЛЬКО на обращение к атрибуту модуля: внутри модуля чтение
  глобального имени его не вызывает.
* **Почему тесты не видели:** 12+ мест в
  `tests/ui/windows/test_document_import.py` делают
  `monkeypatch.setattr(module, "read_document", …)`. Сам `setattr` сначала
  читает атрибут (`getattr`) — и тем самым РЕГИСТРИРУЕТ настоящее имя в
  `globals()`. То есть тест лечил дефект до того, как тот успевал
  проявиться.
* **Почему линтер не видел:** в `.ruff.toml` этот файл был в
  `per-file-ignores` с пометкой «ложные F821». Проверка показала: **F821
  был правдой, а не ложью** — `ruff --select F821` на старом коде даёт
  ровно два попадания, и оба оказались настоящими (второе — `DataMapper`
  в том же файле, там имя регистрировалось на импорте, то есть в работе
  было безопасно, но оставалось невидимым для линтера).
* **Исправление** (`8925f3d`, `d4ad525`): имя берётся через
  `sys.modules[__name__].read_document` — тот же приём, что уже применён в
  этом файле для `DataMapper` и описан в шапке; `monkeypatch` в тестах
  продолжает работать, потому что имя читается в момент вызова. Исключения
  F821 для `import_service.py` и `core/mirror.py` сняты — теперь линтер
  эти имена проверяет.
* **Регресс-тест:** `test_process_reads_real_file_without_patching` в
  `tests/ui/windows/test_document_import.py` — ничего не подменяет, читает
  настоящий DOCX. Проверено, что **без исправления он падает** (тот самый
  `NameError`), а с исправлением проходит.

### 2. ИСПРАВЛЕНО: `core.mirror.current_target_data` — тот же дефект

`NameError: name 'TARGET_PROFILES' is not defined` при вызове в свежем
процессе: имя приходит из приватного `core/mirror_targets.py` через
модульный `__getattr__`, а читалось как обычная глобальная. Рядом, в
`collect_conflicts`, стоит правильный вызов `target_profiles()` — то есть
дефект был расхождением внутри одного файла.

Исправление `2a60e65` — одна строка, семантика та же (модульный
`__getattr__` для `TARGET_PROFILES` возвращает ровно `target_profiles()`).
Вызовов у функции в проекте нет (только определение и `__all__`), поэтому
это латентный дефект, а не рабочий отказ; регресс-тест не добавлен
сознательно — новой файл-единицы тестов это стоило бы правки стража
раскладки, а функция пока никем не используется.

### 3. НЕ ИСПРАВЛЕНО: GigaChat недоступен с этой машины

`SSLError: SSLCertVerificationError` при получении токена
(`ngw.devices.sberbank.ru:9443`). Следствия, замеренные, а не
предполагаемые:

* правовой RAG работает без эмбеддингов GigaChat — на локальной модели
  `local-bow-512` (индекс: 20 документов, 16 592 фрагмента, 32,4 МБ);
* облачное распознавание (Vision) в живом прогоне не проверено;
* правовой поиск по времени: **6,3 с** первый запрос в процессе (загрузка
  индекса), **1,4 с** последующие; внутри цикла агента — 5–10 с, потому
  что к поиску добавляется маскирование ответа инструмента (3 488 знаков
  ответа → 1,5 с на маскирование, замерено отдельно).

Это про сеть и окружение, а не про код.

### 4. НЕ ИСПРАВЛЕНО: `import services.recognition.recognizer` первым падает

Воспроизведение (свежий процесс):

```
python -c "import services.recognition.recognizer"
AttributeError: partially initialized module … has no attribute 'DataMapper'
```

Причина: `recognizer` → `from core.dates import to_iso` → `core/__init__` →
`import_service` → на строке 192 ему нужен `DataMapper` из ещё не
достроенного `recognizer`. Порядок «сначала `core`» (как в приложении,
`main.py`) и порядок через алиасы (`core.recognizer`) работают;
`tools/check_stage2_aliases.py` проходит. То есть это ЛАТЕНТНАЯ
хрупкость порядка импорта, а не отказ приложения.

Чинить — значит делать `SCHEMA` ленивой (сейчас она строится на импорте из
полей `DataMapper`, а её импортируют 10+ модулей). Это изменение публичного
контракта, а не однострочник, поэтому здесь не делалось: нужно решение
владельца.

### 5. Наблюдение: `delete_contract` в проекте нет

Сценарий «сохранить → найти → удалить» из промпта проверен без удаления.
Изолированная база удаляется вместе с временной папкой, так что мусора не
остаётся, но функции удаления договора в `db/crud/` нет вовсе.

### 6. Наблюдение: тесты могут «лечить» дефект подменой того же имени

Пункт 1 — не единичный случай, а класс риска: если тест подменяет имя через
`monkeypatch.setattr(module, "<имя>", …)`, он тем самым создаёт это имя в
модуле, и настоящая ошибка «имени нет» становится ненаблюдаемой. Проверять
такие места надо тестом БЕЗ подмены (как добавленный регресс-тест).
